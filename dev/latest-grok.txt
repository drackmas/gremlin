Refactor and harden the Gremlin codebase at https://github.com/drackmas/gremlin (local self-contained Python agentic chat assistant with tool-calling loop, OpenAI-compatible backend, Flask UI + CLI + Discord + API bridge).

Goal: Make it cleaner, more reliable, more extensible, and production-ready while preserving the existing architecture and all current functionality. Then implement a powerful meta-capability so the bot can autonomously create, register, and use new skills and tools on demand.

### Core architecture to preserve
- ChatManager.run() agentic loop (tools → observations → continue until done or MAX_TOOL_ITERATIONS)
- ToolRegistry with Tool dataclass (name, description, JSON-schema parameters, handler → str)
- Skills as pure instruction files: skills/<slug>/SKILL.md with simple --- frontmatter (name, description)
- load_skill tool
- Sandboxed FS tools, run_command, grep/find, YouTube (yt-dlp), memory store, task planner
- System prompt injection of tools + skills + pinned memory + identity + time
- Context management: turn window + token estimate + auto-compaction
- Multiple front doors sharing the same ChatManager
- Sanitize untrusted content (YouTube etc.)

### Issues and problems I notice (fix all of these)

1. Packaging & structure
   - pyproject.toml is tooling-only (ruff/mypy). No [project] table, not installable as a package. Flat script-style imports. Hard to develop, test, or distribute.
   - requirements.txt has no version pins.
   - Mixed root-level modules (app.py, cli.py, discord_bot.py, sessions.py, config.py, utils.py) vs packages.
   - ensure_dirs only creates sessions + data; transcripts, tasks, etc. created ad-hoc.

2. Tool & skill system is static / incomplete
   - build_registry() hardcodes every tool. No plugin discovery, no hot-reload for tools, only crude mtime cache for skills dir.
   - Skills are load-only. Model cannot create, edit, or register new skills/tools at runtime.
   - No “meta” tool for extending the system itself.
   - README still mentions some outdated tool names (youtube_summary etc.); actual youtube.py only has youtube_transcript + youtube_video_info.
   - task tool is very basic (only plan/view, no update/complete/status).
   - Shell uses /bin/sh -c with only cwd + timeout; no further command allow/deny list or safer defaults.
   - Argument validation is basic (flat schema, no nested objects/arrays deeply validated, no additionalProperties: false enforced everywhere).
   - Tool handlers sometimes raise custom exceptions that get turned into ERROR: strings; inconsistent patterns.

3. Reliability / robustness
   - File-based session + memory + tasks stores have no locking → race conditions under concurrent web/Discord/bridge use.
   - Token estimation is crude (chars/4). Compaction can fail silently.
   - Bridge is raw socket HTTP (fragile compared to proper ASGI/WSGI or FastAPI).
   - Discord bot and Flask app start logic is a bit tangled.
   - Logging is present but not structured; no request/session correlation IDs everywhere.
   - Error surfaces to the model are sometimes too terse or too verbose.
   - No graceful degradation when the LLM backend is down or returns malformed tool calls (beyond the existing json_repair path).

4. Code quality & maintainability
   - Some large files (chat/manager.py is long).
   - Inconsistent type hints / mypy is very loose.
   - Duplicated path handling and atomic writes.
   - Frontend is basic Bootstrap; no modern build step, limited accessibility/UX polish.
   - Tests exist and look decent, but coverage of edge cases (concurrent access, malformed tool args, skill cache invalidation, dynamic registration) is incomplete. Tests are excluded from mypy.

5. Missing capabilities that hurt usability
   - No built-in way to download YouTube audio (mp3/m4a) or other media.
   - No general “create_file / write_file” convenience beyond edit_file actions.
   - No tool to list/reload skills or tools at runtime.
   - Settings and config scattered between DEFAULT_SETTINGS, env vars, and code constants.

### Required improvements (do these thoroughly)

1. Turn the repo into a proper modern Python package
   - Add full [project] table to pyproject.toml (name=gremlin, version, dependencies with reasonable pins, scripts entry points for gremlin-web, gremlin-cli, gremlin-discord, gremlin-bridge).
   - Keep requirements.txt in sync or generate it.
   - Make the package installable in editable mode (pip install -e .).
   - Clean import structure; prefer absolute imports inside the package.
   - Add a simple Makefile or just document the new install/run flow in README.

2. Harden existing systems
   - Add file locking (or switch critical stores to SQLite) for sessions, memory, tasks.
   - Improve ToolRegistry validation (support nested schemas better, reject unknown properties by default, better error messages).
   - Make shell safer by default (optional allow-list of common safe commands, or at least document the risk clearly and add a config toggle).
   - Better structured logging with session_id correlation.
   - Make context token estimation slightly smarter or configurable.
   - Ensure all runtime directories are created cleanly via ensure_dirs.
   - Update README to match reality (current tools, skills list, architecture diagram if needed).
   - Keep and expand the test suite; add tests for the new meta capability.

3. Code cleanup
   - Extract large methods, reduce duplication, improve type hints where it helps.
   - Consistent error handling patterns for tools (prefer returning ERROR: strings; reserve raises for truly unexpected cases).
   - Make SkillLoader cache more robust (watch individual file mtimes if needed).
   - Keep the existing front doors working unchanged from the user’s perspective.

### CRITICAL NEW FEATURE: Meta-skill / self-extension capability

Implement a first-class way for the bot to create and register new skills AND tools on demand so that requests like:

“make a skill to convert this youtube video to mp3”

…work end-to-end automatically.

Requirements for the meta capability:

- Add a new tool (or small set of tools), e.g. `create_skill` and/or `create_tool` / `register_extension`, that the model can call.
- Workflow the model should follow (encode this clearly in a new skill called something like `skill_creator` or `extension_builder`):
  1. Check whether a suitable skill or tool already exists (list skills / list tools).
  2. If not, decide whether a pure skill (instructions only) is enough or a new executable tool is required.
  3. For a skill: write a proper skills/<slug>/SKILL.md with frontmatter + clear step-by-step instructions that use existing tools (or newly created ones).
  4. For a tool: generate a new Python module under tools/ (or a plugins/ directory) that follows the exact existing Tool pattern (build_xxx_tools function returning list[Tool] or a single Tool). The tool must be sandboxed and safe.
  5. Register the new tool into the live ToolRegistry (hot-reload / dynamic register) so it is immediately available in the current and future sessions without restarting the process.
  6. Invalidate/reload the SkillLoader cache so the new skill appears in the system prompt and load_skill works.
  7. Confirm success and show the model how to use the new capability.
  8. Prefer reusing existing tools (yt-dlp already present) rather than reinventing.

Concrete example that must work after the change:
User: “make a skill to convert this youtube video to mp3”
→ Model checks for existing skill/tool → creates skills/youtube_to_mp3/SKILL.md that instructs using a new (or existing) tool → if needed creates tools/youtube_audio.py with a youtube_to_mp3(url, output_path?) tool that uses yt-dlp to extract audio → registers it → returns the skill name and usage instructions → subsequent turns can call load_skill("youtube_to_mp3") and then the tool.

Safety constraints for the meta tools:
- All generated code and files must stay inside the project sandbox.
- New tool handlers must follow the same security model as existing ones (path sandboxing, timeouts, output truncation, sanitize_untrusted where appropriate).
- Do not allow arbitrary unrestricted code execution; the create_tool path should generate and import only well-formed Tool modules, or provide a safer restricted way to add handlers.
- Log every creation/registration.
- Provide a way to list and (optionally) remove/disable dynamically created extensions.

Also add a corresponding skill (skills/skill_creator/SKILL.md or similar) that teaches the model exactly when and how to use the meta tools.

### Delivery expectations

- Do not break existing sessions, settings, or the four front doors.
