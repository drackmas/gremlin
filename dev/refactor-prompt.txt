Act as a senior software engineer specializing in large-scale refactoring.

First inspect the entire repository without modifying files. Understand the architecture, major modules, dependency relationships, build system, tests, and public interfaces.

Identify:

duplicated or conflicting logic
overly complex functions/classes
inappropriate abstractions
tight coupling
circular dependencies
dead or unreachable code
inconsistent error handling
poor separation of concerns
performance problems caused by architecture
missing or weak tests
outdated patterns/dependencies
Rank each issue by impact, confidence, and refactoring risk.

Then create a phased refactoring plan. Each phase should be small enough to review independently and should preserve externally observable behavior.

Before implementing a phase, explain:

What is changing
Why it is changing
Which files will change
What behavior must remain unchanged
What tests protect against regressions
Implement only one phase at a time. After each phase, run the relevant tests, type checker/linter, and build. Fix failures before continuing.

Do not perform broad stylistic rewrites, rename public APIs unnecessarily, introduce dependencies without justification, or change behavior unless explicitly requested.

At the end of each phase, summarize the changes, tests run, remaining risks, and recommended next step.
